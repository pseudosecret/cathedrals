# First complete work

The next live acceptance target is eight scenes and two endings, through the same
Genesis, backward scaffold, forward writing, semantic analysis, validation and
static publication pipeline used for larger works. The operator starts the live
run; engine revision tests use a synthetic provider with network access blocked.

Requests of 8–12 scenes derive one artifact, two terminal outcomes, no required
formal compositions, one branch pressure and no reconvergence pressure. They use
one or two arcs, at most four macro attractors and six obligations. These are
structural bounds; the model still chooses the story, targets and chapter/branch
placement. Larger requests retain their existing guidance. Reconvergence remains
available, and a chapter still has one authored continuation.

## Ending prerequisites

Outcome planning receives the actual obligation definitions. Selecting a hard
prerequisite makes its complete dependency closure explicit in every alternative
entry case. The engine copies the existing obligation descriptions into required
conditions; it does not claim they have happened. Backward predecessors must earn
these conditions through the existing support bindings. Required conditions cannot
be dropped to meet the eight-condition interface bound; an oversized draft needs
correction before Architecture freezes. An outcome's own terminal transformation
belongs in that outcome, not in its prerequisites.

## One-pass failures

Valid prose remains immutable, including while staged. Each unsupported source
audit task gets one evidence-only reconsideration, using the same permitted
original sources. A reversal requires exact quotations and an explanation of the
original objection. Both responses and their usage remain in the ledger. Resuming
after an interruption reuses both responses instead of requesting another opinion.

If the promise remains unsupported, the run fails with `continuity_impossibility`.
The diagnostic identifies the promise, incoming route, permitted sources and both
audit histories. The engine cannot fix a missing event under the one-pass rule;
it must not ask the operator to resume identical frozen prose indefinitely.
Metadata/provider interruptions that remain repairable still pause normally.

## Acceptance and operation

Use a fresh execution clone after committing the engine changes. Older runs keep
their saved launcher and do not acquire installation updates. Start `./cathedrals`
and request eight scenes. This document does not authorize an unattended live run
during engine revision.

Accept only `READY_TO_PLAY` with eight populated scenes, two reachable endings,
one readable artifact, complete source exports and a working static reader. The
launcher prints the actual build directory and local server command. Published
output lives at `generated-work/<generation_id>/web/dist` in the execution clone.
Check every branch and both endings in the browser before increasing the scope.

If interruption occurs after the site directory is published but before success
is recorded, resume verifies matching finalization/provenance and every projected
file, then finishes the status update without contacting the model or replacing
the published site. Conflicting output is an integrity failure.

Use existing phase usage summaries, raw responses, context receipts and failure
diagnostics to investigate a failed trial. Do not treat a synthetic publication
as evidence of live-model reliability. First establish the eight-scene result,
then assess 30 and 150 scenes. Larger reconvergent works still face the 128-state
verification limit and growth in mandatory source context; this milestone does
not establish 5,000-scene readiness.
