# Bounded execution and acceptance

New interactive runs freeze `execution_policy` in the immutable manifest. Existing runs retain their original launcher and policy. Installation updates never replace a run's snapshot.

The compiler requests a small macroarchitecture layout, allocates stable IDs, and authors coherent macro records in batches of at most four. Scaffold planner 3 separately selects target entry cases, declares one immediate predecessor, and binds evidence in checkpointed tasks of up to four scenes. These choices are automatic; linear chapters and branches remain available. Accepted fields survive repairs. Foreign key schemas constrain known arcs, obligations, attractors, entities and topology nodes. Reference repairs cannot expand a compiled layout by inventing more obligations. Cycles and disconnected routes still require model decisions; the engine constructs their envelopes and checks the resulting graph. Current checkpoints preserve accepted contracts and fields. Older checkpoint formats execute only through their saved launchers.

Planning calls contain frozen law and brief, global world canon, compact source/entity/plan catalogs, retained target records and referenced neighbors. They do not routinely send the entire assembled draft and cast. Packet context includes global world and composition law, relevant entities and current constraints, assigned obligations, complete mandatory prerequisite evidence and deterministic predecessor contracts. Contracts contain typed changes and navigation with commit/hash references; they do not replace literary evidence with generated summaries. Mandatory context that exceeds capacity pauses explicitly.

SQLite index version 3 adds `staged_items`. Each row identifies the checkpoint revision, record pointer, allocated ID and `TENTATIVE PLAN` authority. Checkpoint JSON remains authoritative. The projection rebuilds from those files and is separate from committed FTS documents. Committed literary archives remain authoritative and immutable.

The selected model receives synthetic native tool and structured metadata checks before Genesis. LM Studio's supported `tool_choice: "required"` string forces the synthetic tool check. Successful checks freeze `retrieval_mode: tools`; an unusable tool response freezes `automatic` fallback. The selected model and reasoning settings are preserved. The synthetic requests, responses, parameters and actual usage are archived and ledgered in the new run.

Four bounded tools expose typed reads: `search_records`, `get_records`, `get_constraints`, and `get_plan_items`. They accept no SQL, file paths or writes. Text searches escape literal terms; record reads verify archived hashes. Model retrieval is a separate analysis stage, with at most two rounds, eight calls, and one argument-correction opportunity. Authoring retains strict response schemas and has no tools. Model reads and automatic optional sources share the 24-unit/12,288-token retrieval allowance. Input, output, cumulative and analysis safeguards remain binding.

Completed streams require a finish reason and `[DONE]`. Tool IDs, names and arguments may arrive in fragments and multiple call indices; incomplete streams execute no calls. Completed retrieval sessions preserve their working set, revision, round messages and results. Resume reuses completed rounds and ledger entries rather than billing their usage twice. Per-phase progress reports calls, input/output/reasoning tokens, retries and retrieval mode.

Proposition existence now includes all historically established facts. Replacing a fact in current truth does not erase the proposition needed to validate earlier beliefs. Current-state selection and epistemic consistency checks remain separate.

The browser reader isolates theme and story-state scripts so their variables cannot collide. New-policy complete-work validation rejects a graph with no reachable ending. The browser acceptance harness separately exercises an actual condition-valid path; mere file existence is insufficient.

## Verification

Run `python3 -m unittest discover -s engine/tests` and `python3 engine/tests/validate-generation-protocol.py`. `test_thirty_scene_acceptance.py` exercises a complete synthetic 30-scene run, including focused reference, semantic and epistemic recovery and interruption/resume, then checks `READY_TO_PLAY`, immutable literary bytes and exact usage accounting.

To export that synthetic publication for browser testing:

```sh
CATHEDRALS_ACCEPTANCE_EXPORT=/tmp/cathedrals-synthetic-30 python3 -m unittest discover -s engine/tests -p test_thirty_scene_acceptance.py
python3 -m http.server 4327 --bind 127.0.0.1 --directory /tmp/cathedrals-synthetic-30
```

Browser tooling is isolated under `engine/tools/browser`; see its README. A live acceptance run must use a fresh execution copy with an explicitly revised phase gate. Keep the foundation in `engine_revision`, preserve old attempts and snapshots, and do not describe synthetic publication as generated literature or evidence of 5,000-scene readiness.
